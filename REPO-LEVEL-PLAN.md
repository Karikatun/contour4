# Создание новой карты R.E.P.O.

Стандартная карта R.E.P.O. — набор prefab-модулей, из которых игра собирает рейд. Базовый путь для новой карты — свой Level Preset, LevelContent с модулями и экспорт через REPOLib SDK. Первый прототип проверяет весь цикл рейда на серой геометрии. Фиксированная раскладка с собственными событиями требует отдельной проверки способа генерации, как у установленного PT. [Руководство REPOLib по уровням](https://repomods.com/apis/repolib/sdk/levels.html)

## Как игра собирает карту

1. **Level** задаёт имя карты, параметры генерации, лут, музыку, атмосферу и загрузочную графику. В **LevelContent** указываются Level, prefab-ы модулей по ролям, по необходимости общий объект открытого стыка и заглушка. Для обычного рейда применяется LevelType.Normal.
2. **REPOLib 4.5.1** сканирует .repobundle в BepInEx/plugins. LevelContent.Initialize вызывает Levels.RegisterLevel(LevelContent). Библиотека регистрирует сетевые prefab-ы модулей и заполняет списки PrefabRef в Level. Ключи модулей строятся по схеме Level/{уровень}/{категория}/{prefab}, поэтому имена Level и prefab-ов внутри категории должны быть уникальными. Уровень попадает в соответствующий список RunManager.
3. **LevelGenerator** на хосте или в соло формирует сетку, выбирает стартовую комнату и остальные модули, размещает объекты стыков и заглушки. В кооперативе SpawnModule вызывает PhotonNetwork.InstantiateRoomObject. Затем игра готовит предметы, строит NavMesh на собранной геометрии, размещает игроков и врагов. В проверенной сборке NavMesh строится асинхронно через UpdateNavMeshDataAsync. Ручная проверка одного prefab в Unity покрывает только его геометрию и компоненты.

Цепочка сверена статически по `Assembly-CSharp.dll` и `REPOLib.dll` из установленной игры и профиля NewPack. В `resources.assets` игры найдено 445 компонентов Module, а также ModulePropSwitch, LevelPoint, RoomVolume, NavMeshModifier, DirtFinderMapFloor/Wall/Door и ExtractionPoint. Среди стартовых prefab-ов видны варианты Manor с разными планировками, включая Loungey и Corridor. [Документация загрузки бандлов](https://repomods.com/apis/repolib/api/bundles.html) · [Исходники REPOLib](https://github.com/ZehsTeam/REPOLib)

### Роли модулей

| Роль | На что влияет | Первая сборка |
| --- | --- | --- |
| Start Room | Точка входа, грузовик и стартовая эвакуация. Генератор выбирает один вариант на рейд. | Один оригинальный по планировке модуль с проверенными компонентами грузовика. |
| Normal | Основная комната. Четыре стороны меняют состояние при стыковке. | Два различимых варианта, каждый стыкуется во всех используемых направлениях. |
| Passage | Два противоположных входа. | Один проход с проверкой ширины под тележку. |
| Dead End | Тупик с одним входом. | Один тупик, где игрок может развернуться с грузом. |
| Extraction | Место эвакуации с одним входом. | Один вариант prefab. Число точек в забеге проверяется по правилам генерации и прогрессу. |
| Special / Mega | Дополнительные роли, присутствуют в Module.Type, Level и LevelContent текущей сборки. | Подключать только под требования карты после проверки стандартных модулей. |

Для обычного модуля исходный ориентир SDK — ячейка 15 × 15 м, центр prefab в начале координат, стыки по серединам сторон на X/Z ±7,5 м. Для Passage это противоположные стороны, у Start Room точка стыка по шаблону находится в начале координат. Высоту пола, поворот и габариты сверять со стандартным образцом своего типа. У Normal для каждой стороны задать ConnectedParent и NotConnectedParent в ModulePropSwitch с соответствующей ориентацией. Отдельно проверить закрытый вариант, коллизию и отрисовку на карте. Mega имеет собственный контракт размеров и соединений. [Геометрия и соединения в REPOLib SDK](https://repomods.com/apis/repolib/sdk/levels.html#modules)

Списки 1/2/3 задают пулы для категорий. В текущем PickModule пустые пулы получают нулевой вес. Начать можно с пула 1, а затем проверить целевые настройки прогрессии и добавить разнообразие. Для первого прототипа состав из таблицы — рабочая гипотеза, которую нужно подтвердить полной генерацией и эвакуацией. [Руководство по LevelContent](https://repomods.com/apis/repolib/sdk/levels.html#creating-a-level-content-object)

## Универсальный порядок работ

| Этап | Что сделать | Условие перехода |
| --- | --- | --- |
| 1. Идея | Записать тему, основной маршрут игрока, одну отличительную особенность, целевые режимы и диапазон прогрессии. Определить, нужна ли процедурная сборка или фиксированная раскладка. | Ясно, что должен испытать игрок и что входит в первый рейд. |
| 2. Контекст | Сверить установленную игру, редактор, SDK/patcher, BepInEx и REPOLib. Подготовить отдельный Built-In 3D Unity-проект с игровыми скриптами, слоями и тегами. Локально изучить по одному подходящему стандартному prefab каждой роли и проверить импорт, сериализацию и экспорт. | В Unity нет ошибок компиляции и Missing Script на образцах. Экспорт проходит и пакет загружается в изолированном тестовом профиле. |
| 3. Спецификация | Нарисовать схему маршрутов и матрицу модулей. Задать стыки, проходы для тележки, лут по размерам, выходы, опасные места, свет и звук. Выбрать минимальный набор prefabs. Привязать требования REQ к критериям AC, определить проверки соло и кооператива. | Для каждого модуля известны роль, размеры, стыки и игровой сценарий проверки. |
| 4. Серая геометрия | Сделать Start Room, два Normal, Passage, Dead End и Extraction. Добавить коллизии, состояния стыков, точки лута, RoomVolume, DirtFinder и LevelPoint. Завести Mod, Level и LevelContent. Для первой сборки использовать встроенный generic-лут. Экспортировать и пройти рейд. | Карта загружается. Игрок с тележкой проходит стыки, вывозит лут, завершает эвакуацию и переходит дальше. Враг проходит основной маршрут. |
| 5. Вариативность | Добавить комнаты и повторить тесты стыков при поворотах, нескольких генерациях и разных стадиях прогрессии. Добавлять вертикальность, большие и особые комнаты по одной и проверять последствия для путей и миникарты. | Сгенерированные комнаты достижимы. Нет наложений, провалов, тупиков в обязательных маршрутах или заблокированных экстракций. |
| 6. Арт и механики | Заменить серые меши оригинальными, добавить материалы, освещение, звук, загрузочную графику и нужный тематический лут. Сохранить проверенные проёмы, коллизии и точки навигации. Если требуется C#, выделить одну механику, определить владельца состояния и события, которые увидит клиент. | Каждый изменённый модуль повторно проверен с лутом, тележкой и врагами. Для механики есть сценарии основного, граничного и ошибочного действия. |
| 7. Приёмка и пакет | Собрать ZIP и установить именно его в чистую среду. Повторить тесты со стандартным набором модов владельца, если он входит в цели. Зафиксировать хеш, состав профиля, логи, результаты и оставшиеся ограничения. | Пройдены обязательные сценарии на версии из ZIP. Владелец принимает игровой результат отдельно от технических проверок. |

### Карточка модуля

Копировать на каждый prefab. Для первой карты достаточно одной таблицы модулей, схемы стыков и пометок на серой геометрии.

~~~text
ID и роль:
Пул 1/2/3 или Start/Special:
Границы, направление входа, высоты пола:
Стороны и повороты, Connected/NotConnected:
Проход игрока, тележки и самого крупного целевого груза:
Компоненты и триггеры грузовика/эвакуации (по роли):
LevelPoint и стыки NavMesh:
RoomVolume и элементы DirtFinder:
Места лута, видимость и доступность:
Свет и звук, источники ассетов:
Как воспроизвести проверку:
~~~

- **Навигация.** Разметить ходовой пол и препятствия через NavMeshModifier по шаблону игры. Привязать внешние LevelPoint к стыкам, внутренние — к маршрутам внутри. Ссылки ConnectedPoints сделать взаимными, внешние соединять через внутренние. Сверить точки с итоговым NavMesh. Руководство SDK исключает LevelPoint из модулей Extraction. [Level Points и NavMesh](https://repomods.com/apis/repolib/sdk/levels.html#level-path-points)
- **Карта и объёмы.** RoomVolume покрывает ходовую область, остаётся внутри модуля и использует ожидаемые collider, script и layer. DirtFinder Floor/Wall/Door повторяют фактические полы, стены и двери. Для этажей проверить отметки и раскрытие помещений. [Room Volume и DirtFinder](https://repomods.com/apis/repolib/sdk/levels.html#room-volume)
- **Лут и ресурсы.** Стартовый Level с пустым ValuablePresets использует generic-лут. Разместить `ValuableVolume` и проверить свободное место по используемым категориям размера. Для дополнительного ванильного пресета проверить proxy с точным именем, а для своего лута — собственные Content/prefab и ссылки по целевой версии SDK. Проверить размер груза, коллизии, точки появления и доступность переноса. В ZIP включать собственные или разрешённые ассеты, без копий извлечённых ресурсов базовой игры. [Proxy Valuable Presets](https://repomods.com/apis/repolib/sdk/levels.html#proxy-valuable-presets)
- **Экспорт.** Проверить корневые manifest.json, README.md и icon.png 256 × 256, зависимости по версиям, .repobundle и DLL при необходимости. Сохранить Unity-исходники с .meta, сверить содержимое ZIP и записать SHA-256. [Экспорт из REPOLib SDK](https://repomods.com/apis/repolib/sdk/start.html#export-a-mod) · [Формат Thunderstore](https://wiki.thunderstore.io/mods/creating-a-package)

### Матрица приёмки

| Проверка | Что фиксировать |
| --- | --- |
| Загрузка | Точный ZIP, хеш, версии, строки загрузки бандла и регистрации уровня. Проверить отсутствие ошибок генерации, дубликатов ключей и неразрешённых ссылок, влияющих на карту. |
| Варианты генерации | Прогрессия, seed при доступности или ID прогона и список/схема комнат. Для первого прототипа запланировать минимум три независимые генерации и повторный заход. Для релиза заранее задать покрытие по ролям, поворотам и прогрессии. |
| Маршруты | Прохождение с тележкой и крупным грузом от дальнего модуля до каждого обязательного выхода, в том числе через двери и перепады. У врагов проверить переходы между комнатами и поведение у препятствий. |
| Игровой цикл | Выход из грузовика, появление и перенос лута, сдача квоты, работа кнопки/платформы, завершение рейда, загрузка следующего этапа. Сверить проявление комнат и дверей на миникарте. |
| Кооператив | Хост и реальный клиент видят одинаковые комнаты, двери, лут и ход эвакуации. Проверить взаимодействия с обеих сторон и второй рейд в той же сессии. |
| Пакет и нагрузка | Установка ZIP с объявленными зависимостями, удаление в тестовой среде. Для самого тяжёлого сценария сравнить загрузку, FPS и память с заранее выбранной контрольной картой на том же профиле. |

Перед первым запуском проверить раздельность пользовательских данных игры и тестового профиля. Вести для каждого прогона версию, режим, условия, ожидание, наблюдение и ссылку на доказательство. Размер карты, число комнат и пределы нагрузки устанавливать под конкретную идею. ### Проверка покрытия материалов после сборки помещения

Если на кадре видна однотонная поверхность, воспроизведи тот же ракурс, найди объект лучом из камеры и зафиксируй полный путь рендерера. Проверь эту поверхность на точной базовой сборке и на кандидате. В 0.2.48 этот способ связал видимый однотонный корпус с `shaft-plant/Work bays[13]/Isolator and bypass pumps[4]` и подтвердил появление отделки на том же объекте. [Сравнение корпуса](local-evidence/contour4-material-coverage/shaft-pump-before-after.png)

Для проверки всей карты сними перечень материалов исходного префаба и повтори его после полной сборки помещения. Проверь реально подготовленные префабы и принудительную процедурную сборку, оба стартовых бокса, кольцо с входом, процедурные переходы и детали, добавляемые в конце сборки. Для каждого рендерера запиши его путь, меш, число подмешей, индекс каждого слота `Renderer.sharedMaterials`, шейдер, материал и текстуры. Если количество слотов и подмешей различается, сохрани оба значения и разберись с назначением. Для стекла, обозначений, светящихся и уже текстурированных поверхностей укажи причину сохранения исходного материала. [Unity Renderer.sharedMaterials](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/renderer/sharedmaterials) · [Unity Mesh.subMeshCount](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/mesh/submeshcount)

Сопоставь записи базы и кандидата по пути и индексу, проверь утрату отделки и непрозрачные поверхности без объяснённого исключения. Сравни геометрию, коллизии и свет в тех же условиях. В ранней пробе 0.2.48 поиск подстроки `meter` принял часть имени настила `diameter-deck` за обозначение прибора и исключил настил из отделки. Повторная сверка подтвердила бетон на настилах всех восьми подготовленных вариантов сферы. Результат относится к перечисленным сборкам модулей и трём раскладкам с фиксированными seed в Unity. Для вывода об игровом отображении нужен отдельный прогон R.E.P.O. после разрешения владельца. [Ранняя проба](local-evidence/contour4-material-coverage/first-probe-analysis/coverage-summary.json) · [Итоговые записи по слотам](local-evidence/contour4-material-coverage/slot-dispositions.tsv)

При сплошной окраске стен проверь закрытые грузовые стыки и визуальные накладки. В первой пробе 0.2.50 материал уже покрывал стеновые секции, а старая накладка `spur-plug[16]/Inset cladding[4]` занимала видимую плоскость у проёма приёмной. Луч из обеих камер дошёл до одного коллайдера, а перед ним нашёл выступающий рендерер накладки. Для неиспользуемого грузового стыка примени отделку и к заглушке, которая продолжает стену. Задавай высоту полосы от пола комнаты. В Unity сравни угол и проём в одной позе камеры, затем поверни комнату целиком и повтори кадр. Проверка подтвердила переход окраски через заглушки и совпадение коллайдеров с 0.2.49. ## Как завести конкретную карту в repo-modding

В указанном repo-skills уже есть общие навыки workflow, изоляции, упаковки и проверки Unity. Главная страница перечисляет специализации по монстрам. Для карты использовать существующий тип level в локальном OpenSpec-процессе и заполнить дизайн модулей и матрицу выше. [Karikatun/repo-skills](https://github.com/Karikatun/repo-skills)

В рабочем каталоге repo-modding, когда появится конкретная карта:

~~~powershell
.\modflow.ps1 new <id> level
.\modflow.ps1 os instructions idea --change <id> --json
.\modflow.ps1 status <id>
# После заполнения артефактов проекта
.\modflow.ps1 os validate <id> --strict
.\modflow.ps1 check <id> ready
~~~

Последовательность артефактов — proposal.md → context.md → design.md и требования → verification.json и tasks.md → сборка → evidence.json → приёмка. В state.json вести решение по замыслу и следующее действие. Проверки сборки и игрового прохождения записывать по факту, с точной версией пакета.
